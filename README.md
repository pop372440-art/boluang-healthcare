# บ่อหลวง Health Care

ทะเบียนสุขภาพเจ้าหน้าที่ เทศบาลตำบลบ่อหลวง มีแผนที่ ตาราง สถิติ ตัวกรอง และบันทึกผลตรวจ ใช้ข้อมูลจริงจาก Supabase ไม่มีชุดข้อมูลผู้ป่วยฝังในเว็บ ไม่มีโหมดจำลองผลตรวจ

## การตั้งค่าก่อนใช้งาน

1. ตั้ง `SUPABASE_URL` และ `SUPABASE_ANON_KEY` ใน Vercel เฉพาะฝั่งเซิร์ฟเวอร์ ห้ามใช้ service role key ใน frontend
2. ผู้ดูแลโครงการต้องเลือกบัญชีเจ้าหน้าที่ที่ถูกต้อง แล้วตั้ง `app_metadata.healthcare_role` เป็น `viewer`, `clinician` หรือ `admin` ผ่าน Supabase Admin API/Dashboard โดยไม่ใช้ `user_metadata` สำหรับสิทธิ์ ไม่ควรเดาบัญชีหรือเลื่อนสิทธิ์ทุกบัญชีอัตโนมัติ
3. บัญชี viewer/clinician ต้องมี `app_metadata.healthcare_villages` เป็น array ตัวเลขหมู่บ้านที่ได้รับมอบหมาย เช่น `[1,2,3]` บัญชี admin เข้าถึงทั้งทะเบียน จึงควรมอบให้เฉพาะผู้รับผิดชอบจริง
4. ตรวจนโยบายเดิมและรัน `db/audit-access.sql` บนโครงการที่ถูกต้อง จากนั้นตรวจ RLS ด้วย `tests/rls-check.sql` (อ่านอย่างเดียวและ rollback) ก่อน deploy หน้าเว็บ ผู้ใช้ต้องเข้าสู่ระบบใหม่หลังเปลี่ยนสิทธิ์
5. Deploy branch นี้ผ่าน Vercel ใช้ Node 22 ขึ้นไป ตรวจล็อกอิน บัญชีไม่มีสิทธิ์ การกรองหมู่บ้าน และการบันทึกด้วยบัญชีที่ได้รับมอบหมายจริง

**ยังไม่มีการกำหนดบัญชีหรือรัน migration บน production อัตโนมัติ** เพราะบัญชีเดิมยังไม่มี healthcare_role การเปิดใช้งานต้องเลือกผู้ดูแลให้ชัดเจนก่อน เพื่อไม่ให้เจ้าหน้าที่ทุกคนถูกล็อกออก

## สิ่งที่แก้จาก Audit

- API ตรวจตัวตนจาก Supabase ทุกคำขอและตรวจสิทธิ์จาก app_metadata, session cookie เป็น HttpOnly/Secure/SameSite Strict ไม่มี token หรือเวชระเบียนใน localStorage
- ไม่ส่ง URL Apps Script หรือคีย์ผ่าน `/api/config` และไม่เรียก Google Sheets สาธารณะจากเบราว์เซอร์
- ยอดรวมจากทะเบียนที่โหลดจริงครบทุกหน้า และใช้ตัวกรองเดียวกันสำหรับ KPI ตาราง แผนที่ สถิติ CSV แสดงจำนวนรายการ ไม่อ้างจำนวนคน 920 ราย
- สูตรคัดกรองเดิมรวมอยู่ใน `lib/health-model.mjs` ใช้ร่วมกันบน API และเว็บ ค่าที่ขาดไม่แทนด้วยค่าปกติ หากข้อมูลไม่ครบและไม่พบค่าที่ถึงเกณฑ์เสี่ยง จะแสดง “ข้อมูลไม่ครบ” ไม่ตัดสินว่าปกติ
- แสดงเหตุผลและเวอร์ชันเกณฑ์ การคัดกรองนี้ยังต้องได้รับการทบทวนจากทีมคลินิก โดยเฉพาะบริบทการตรวจน้ำตาล ไม่ใช่การวินิจฉัย
- ไม่เปลี่ยนผลตรวจเก่าเพื่อทำให้สถิติตรง ตัวเลขอายุที่ไม่อยู่ใน schema ไม่สร้างขึ้นเอง ต้องตรวจคุณภาพข้อมูลต้นทางแยกต่างหาก
- ใช้ GeoJSON จริงและรองรับ holes/MultiPolygon ไม่ประมาณจำนวนคนนอกเขตจากสัดส่วนตัวอย่าง พิกัดที่ไม่มีและขอบเขตที่โหลดไม่สำเร็จแสดงว่าไม่ทราบ
- รูปแบบเวลาไทย แยกเวลาตรวจกับเวลาซิงค์ ประวัติอ่านจาก sensor_logs จริง ไม่มีการสร้าง 6 แถวจำลอง
- ฟอร์มว่าง ตรวจช่วงค่าบน client/server และบันทึกต่อประวัติด้วย record_version เพื่อป้องกันการเขียนทับเมื่อมีหลายคนบันทึกพร้อมกัน
- ปกปิดชื่อ/ที่อยู่เริ่มต้น ใช้ DOM textContent ป้องกัน HTML injection และป้องกันสูตรใน CSV
- ใช้ CSS ภายในโครงการแทน Tailwind runtime CDN มีตารางแบ่งหน้าและ layout มือถือ

## Google Drive / Google Sheets

ตรวจต้นทาง Drive แล้ว: แท็บ `ผู้มีสุขภาวะพึ่งพิง` มี 6 คอลัมน์ วันเวลา ชื่อ-สกุล ที่อยู่ ละติจูด ลองจิจูด ลิงก์รูปภาพ ไม่มีคอลัมน์ผลตรวจ จึงนำข้อมูลส่วนนี้ไปเติมค่าตรวจไม่ได้ ตัวอ่านใหม่จับคู่ตามชื่อหัวคอลัมน์และคืนค่าตรวจเป็น null

`google_apps_script.gs` เป็น source สำหรับอัปเดต deployment เดิม: GET ไม่คืนข้อมูลสุขภาพ, POST ต้องมี BRIDGE_TOKEN จาก Script Properties ไม่ใช่คีย์ใน URL ไม่มีการเขียนทับตามชื่อบุคคลและไม่มีการเติมค่าตรวจ

โค้ดใน GitHub **ไม่อัปเดต Apps Script deployment หรือสิทธิ์แชร์ใน Drive อัตโนมัติ** ต้องอ่านและตรวจโครงการใน Drive ที่ได้รับอนุญาต แล้วอัปเดต deployment ให้ตรงกัน ห้ามเปิด Web App แบบสาธารณะให้คืนชื่อ ที่อยู่ และผลตรวจ ระวังข้อมูลเดิมที่เคยฝังในประวัติ Git และไฟล์ที่แชร์สาธารณะด้วย

การนำเข้าหรือบันทึกจากชุดตรวจอัตโนมัติพักไว้จนมีรหัสบุคคลที่มั่นคงและเส้นทางที่ยืนยันสิทธิ์แล้ว การเลือกชื่อเพื่อ upsert อาจเขียนทับคนชื่อซ้ำ ไม่ควรเปิดใช้วิธีเดิม

## ทดสอบ

```sh
npm test
```

ชุดทดสอบใช้ข้อมูลสังเคราะห์ ไม่อ่านหรือแก้ผลตรวจจริง ครอบคลุมสูตรคัดกรอง ค่าว่าง ตัวกรอง พิกัด ขอบเขต API สิทธิ์ ข้อมูลชนกัน และการบันทึกประวัติ การทดสอบ UI ด้วย mock ไม่แทนการทดสอบบัญชีจริงหลังติดตั้ง migration
